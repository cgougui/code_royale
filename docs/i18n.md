# Languages (i18n)

The game ships in English (`en`, the source language) and French (`fr`). Every word a player
reads is translated: UI, levels, hints, the API guide, built-in scripts (comments and speech bubbles),
error messages from the engine and the words drawn on the arena canvas.

## Where text lives

Each package keeps its own language rules, and only the edges hold words:

| Layer | Text? | How |
| --- | --- | --- |
| engine | **none** | Player-facing problems are `Message`s: a code plus parameters (`{ code: "runtime.notDefined", params: { name } }`). The list of codes is `MessageParams` in `protocol.ts`. Values shown by `log()` and the debugger are code-like (`[…×3]`, `💎 potion (480, 300)`), so they need no translation; the UI adds words (`Inspected.count`, `kind: "unset"`, `circular`). |
| content | levels, hints, strategies, API guide, fighter/item names, star goals | One typed catalog per language: `packages/content/src/locales/<lang>/`. Game data (`LevelSpec`, `API_SPEC`, star `Goal`s) is shared by all languages. `contentFor(locale)` joins both. |
| renderer | **none** | The app injects a `RendererText` (team bars, waves, tooltips, pickups…). |
| app | everything else, plus the wording of engine and app messages | i18next. One JSON catalog per language: `app/i18n/locales/<lang>.json`. App-level message codes (`AppMessage`, `app/domain/messages.ts`) work like the engine's. |

The battle is the same in every language: only comments and texts differ between translated scripts,
and a test proves that every level fights exactly the same battle in every language.

## How the language is chosen

`app/i18n/index.ts` sets up i18next synchronously (all catalogs are bundled; they are small):

1. the language the player picked last (`localStorage["code-royale:locale"]`, written by the picker in the header);
2. otherwise the browser's languages (`fr-CA` → `fr`);
3. otherwise English. Missing keys also fall back to English.

`useDocumentLocale` keeps `<html lang>`, `dir` and the page title in step. The prerendered boot screen has no words,
since it is built before the language is known.

Untouched starter code follows the language (`isStarterCode`); code the player wrote is never changed.
A battle remembers its locale, so the debugger replays the same red script.

## Adding a language

Say Spanish (`es`):

1. Add `"es"` to `LOCALES` and its own name to `LOCALE_NAMES` in `packages/content/src/i18n.ts`.
2. `npm run typecheck`: TypeScript now lists the two catalogs that are missing.
3. Copy `packages/content/src/locales/en/` to `locales/es/`, rename the export to `es`, translate,
   and register it in `locales/index.ts`.
4. Copy `app/i18n/locales/en.json` to `es.json`, translate, and register it in `app/i18n/resources.ts`.
5. `npm run check`.

Translation rules (checked by `packages/content/test/locales.test.ts` and `app/test/i18n.test.ts`):

- **Code is not translated.** In scripts, hints and examples, translate comments and the texts inside quotes only:
  identifiers, API names (`me.attack`) and type strings (`"knight"`) stay as they are. Tests compare the code
  token by token with English.
- Keep every `{{placeholder}}` and markup tag (`<b>…</b>`, `<line>…</line>`) of the English text.
- Plurals use i18next suffixes (`_one`, `_other`…): give every form the language needs
  (`Intl.PluralRules`; French also needs `_many`).
- Same keys as English, no empty text, same number of hints per level, a `note` for each level with uneven armies,
  and a name for each named fighter (`names`).

## Adding text

- **UI**: add the key to `en.json` (TypeScript types `t()` keys from it), then to every other catalog.
- **A new engine message**: add its code to `MessageParams`, build it with `message(code, params)`,
  and add `messages.<code>` to every catalog. `useFormatMessage` turns any message into text.
- **Content**: add the field to `ContentText`/`LevelText`; TypeScript points at every locale that lacks it.
